# Laravel adapter building blocks

Research for [Laravel adapter building blocks](https://github.com/gomighty/mighty/issues/35), part of [Map: the way to Mighty 0.1.0](https://github.com/gomighty/mighty/issues/29). Verified 2026-09-11 against official documentation and first-party source. This note resolves research questions; recommendations below are inputs to the specification, not new standing decisions.

The adapter can use ordinary Laravel package mechanisms for its public API, Blade compilation, command wrappers, and HTTP transport. The main compatibility conflict is tooling: PHP 8.2 works with Laravel 12, but cannot run Pest 4. The main integration gap is assets across several Blade partial renders; neither recognizing a custom tag nor discovering a sidecar URL solves that by itself.

## 1. Blade tags, attributes, and assets

### Existing implementations

Livewire registers a callable through `app('blade.compiler')->precompiler(...)`. Its tag compiler subclasses Laravel's `ComponentTagCompiler`, recognizes the `livewire:` prefix, parses attributes with Laravel's protected helpers, and emits `@livewire(...)` directives. The inspected implementation handles paired and self-closing tags, slots, dynamic component names, and keys. These are Livewire features, not requirements for Mighty. [Registration](https://github.com/livewire/livewire/blob/90a872f7be8b394c892ede8ac1c2c46557ab1f08/src/Mechanisms/CompileLivewireTags/CompileLivewireTags.php), [tag compiler](https://github.com/livewire/livewire/blob/90a872f7be8b394c892ede8ac1c2c46557ab1f08/src/Mechanisms/CompileLivewireTags/LivewireTagPrecompiler.php).

Flux also subclasses `ComponentTagCompiler`. It recognizes opening, closing, and self-closing `flux:` tags, resolves names into the `flux::` view namespace, and generates normal Blade component directives. Its provider supplies the Blade aliases, namespaces, and compiler instance, then registers `compile()` as a precompiler. A custom prefix is therefore feasible without inventing another template engine. These protected compiler helpers remain framework coupling to cover on both supported majors. [Flux compiler](https://github.com/livewire/flux/blob/d9de8beb3a26226e365490bb8b061025966256c8/src/FluxTagCompiler.php), [provider](https://github.com/livewire/flux/blob/d9de8beb3a26226e365490bb8b061025966256c8/src/FluxServiceProvider.php).

Laravel's attribute parser provides these precise meanings:

| Template attribute | Value passed to component code |
| --- | --- |
| `posts="posts"` | Literal string `posts` |
| `:posts="$posts"` | PHP expression `$posts`, preserving its value/type |
| `:$posts` | Expanded to `:posts="$posts"` |
| `disabled` | Boolean `true` |
| `::class="expression"` | Literal attribute named `:class`, for client-side bindings |

Bare `:posts` is **not** the same shorthand as `:$posts`: binding recognition requires `=`, and the bare attribute path treats it as a boolean attribute. Do not document it as passing `$posts`. Literal attributes use Blade echo compilation and quote escaping; bound expressions can be emitted without HTML attribute sanitization, as Livewire does, because they are component data. [Laravel attribute parser](https://github.com/laravel/framework/blob/38486704d064d8c3dd1c546e9a2d7ffa13d2dfc4/src/Illuminate/View/Compilers/ComponentTagCompiler.php).

Blade stores `@verbatim` and `@php` blocks, removes Blade comments, and compiles its own component tags before running registered precompilers; it tokenizes and compiles directives afterwards. Consequently a precompiler may emit a directive or PHP, but emitting a fresh `<x-...>` tag would miss the native tag pass unless explicitly compiled. [Compilation order](https://github.com/laravel/framework/blob/38486704d064d8c3dd1c546e9a2d7ffa13d2dfc4/src/Illuminate/View/Compilers/BladeCompiler.php).

Livewire's frontend asset manager keeps separate script/style flags, returns an empty string after the first emission, and resets flags on its `flush-state` event. Its automatic injection listener handles successful HTML responses, collects assets, then inserts them into the completed document. That lifecycle matters for repeated components and long-lived PHP workers. Flux's `@fluxScripts` forces Livewire asset injection and emits Flux's script; Flux marks its assets as rendered and uses `data-navigate-once`, but the inspected `scripts()` path does **not** return early when already marked. Client navigation deduplication is distinct from a server-side once-per-response guarantee. [Livewire assets](https://github.com/livewire/livewire/blob/90a872f7be8b394c892ede8ac1c2c46557ab1f08/src/Mechanisms/FrontendAssets/FrontendAssets.php), [automatic injection](https://github.com/livewire/livewire/blob/90a872f7be8b394c892ede8ac1c2c46557ab1f08/src/Features/SupportAutoInjectedAssets/SupportAutoInjectedAssets.php), [Flux directives and script tag](https://github.com/livewire/flux/blob/d9de8beb3a26226e365490bb8b061025966256c8/src/AssetManager.php), [Flux manager](https://github.com/livewire/flux/blob/d9de8beb3a26226e365490bb8b061025966256c8/src/FluxManager.php).

### How we'd do it

Implement a small Mighty-owned precompiler registered by the service provider. Initially support `<mighty:posts.index :posts="$posts" />` and `<mighty:posts.index :$posts />`; have [Laravel adapter spec](https://github.com/gomighty/mighty/issues/44) decide whether the draft's unclosed `<mighty:...>` form must also work and whether paired tags/slots are supported. Generate a call that renders a partial at **view execution**, never at compilation or `view:cache` time.

Treat templates as application code: bound PHP expressions belong to trusted Blade source. Never compile user-supplied template strings, evaluate expressions inside the parser, or interpolate runtime props into generated PHP. Validate component names against the agreed dot-name grammar, quote static names with PHP-safe string serialization, preserve bound values until JSON normalization, and emit only the trusted render result as HTML. Unsupported/malformed tags should yield a clear compile error. Test quotes, `>` inside quoted expressions, booleans, shorthand, comments/verbatim blocks, sibling tags, and cached views on Laravel 12 and 13. These are implementation recommendations based on the compiler behavior above.

Keep a per-request asset registry keyed by asset identity, and agree with the sidecar/core on how partial renders report dependencies. A single Blade `@once` around the first component is insufficient: a later component may need different CSS or hydration code. Decide in [Sidecar design](https://github.com/gomighty/mighty/issues/43) and [Laravel adapter spec](https://github.com/gomighty/mighty/issues/44) whether completed-response injection or explicit layout directives own final placement, including missing `<head>` and Livewire updates/navigation. The current core helper appends assets only when the parsed HTML has an explicit, source-positioned `<head>`; it has no page-wide registry across separate renders. [Current injection helper](https://github.com/gomighty/mighty/blob/6c7ca1d7ffab6494602db5d72720e764b8b00465/packages/core/src/utils/injectTagsIntoHead.ts), [render result types](https://github.com/gomighty/mighty/blob/6c7ca1d7ffab6494602db5d72720e764b8b00465/packages/core/src/types.ts).

## 2. Vite hot files, asset URLs, and missing-build errors

The Laravel Vite plugin defaults to `public/hot` (or `<publicDirectory>/hot`). On the server's listening event it writes a plain UTF-8 URL: the resolved dev-server URL plus the configured Vite base with its trailing slash removed. It is **not JSON** and is not necessarily just an origin. It removes the file on normal exit and handles SIGINT, SIGTERM, and SIGHUP. An uncatchable termination can still leave a stale file; existence does not establish readiness. [Plugin configuration, writing, cleanup](https://github.com/laravel/vite-plugin/blob/a84a487481e3d75df8467f49cedbeb4b23c552b3/src/index.ts).

Laravel's `Vite` class defaults to `public_path('/hot')`; `useHotFile()` can change it. `@vite` invokes that class. `isRunningHot()` only checks `is_file()`. In hot mode, it prepends `@vite/client` to entrypoints, reads and trims the hot file, and appends each asset path. Otherwise it reads `public/<buildDirectory>/manifest.json`, with `build` the default directory, and resolves build entries/imports/CSS. [Blade directive](https://github.com/laravel/framework/blob/38486704d064d8c3dd1c546e9a2d7ffa13d2dfc4/src/Illuminate/View/Compilers/Concerns/CompilesHelpers.php), [Vite implementation](https://github.com/laravel/framework/blob/38486704d064d8c3dd1c546e9a2d7ffa13d2dfc4/src/Illuminate/Foundation/Vite.php), [customization docs](https://laravel.com/framework/docs/12.x/vite#advanced-customization).

A missing manifest throws `ViteManifestNotFoundException` with the expected path; a missing entry throws `ViteException`. The former already extends `ViteException` and is marked deprecated in the inspected Laravel 12 source. Laravel 13 still throws it for a missing manifest. These are synchronous PHP rendering exceptions, so a Blade view may wrap the underlying exception; the normal Laravel exception handler decides the development/production presentation. A stale hot file takes the hot branch instead of checking for a manifest. [Laravel 12 exceptions](https://github.com/laravel/framework/blob/38486704d064d8c3dd1c546e9a2d7ffa13d2dfc4/src/Illuminate/Foundation/ViteManifestNotFoundException.php), [Laravel 13 Vite](https://github.com/laravel/framework/blob/41807417bb85908412b67ff7ec4132a026d603c7/src/Illuminate/Foundation/Vite.php), [Blade exception wrapping](https://github.com/laravel/framework/blob/38486704d064d8c3dd1c546e9a2d7ffa13d2dfc4/src/Illuminate/View/Engines/CompilerEngine.php).

### How we'd do it

Use a separate configurable Mighty discovery file, not Laravel's `public/hot`, so ordinary Laravel Vite and Astro can coexist. Its path, contents, dev/production distinction, separate browser asset URL versus local render URL, stale-file behavior, and readiness handshake belong to [Sidecar design](https://github.com/gomighty/mighty/issues/43). Have the sidecar write it atomically only when ready and remove it only if it still owns that file. Hot-file discovery remains mandatory per the map.

Dev asset tags should point directly to the sidecar's browser-accessible asset endpoint; production build assets should go under an isolated Laravel `public/` directory. Do not assume Astro assets can be found in Laravel Vite's entry manifest. The PHP adapter should produce actionable Mighty exceptions for absent discovery/build artifacts, unreachable sidecars, and render failures, including the relevant path or command (`mighty-laravel dev`, `build`, or `start`). Final exception taxonomy and whether development stack/overlay payloads cross the sidecar boundary remain [Sidecar design](https://github.com/gomighty/mighty/issues/43) and [Laravel adapter spec](https://github.com/gomighty/mighty/issues/44) decisions.

## 3. Starter kit mechanics

The documented community flow is `laravel new my-app --using=vendor/starter-kit`, naming a package available on Packagist. Composer `create-project` obtains that project's files and installs its dependencies; the kit is an application template, not a package installation callback that modifies an existing Laravel app. [Laravel starter-kit docs](https://laravel.com/framework/docs/12.x/starter-kits#community-maintained-starter-kits), [Composer create-project](https://getcomposer.org/doc/03-cli.md#create-project).

The inspected installer replaces the normal `laravel/laravel` create-project command with `composer create-project <kit> <directory> --stability=dev`. It subsequently runs the project's `post-root-package-install` Composer script and `artisan key:generate`. It also recognizes optional `extra.laravel.installer.post-create-project` command arrays. Newer source has a separate URL-based `npx tiged` fallback; that is not needed for the map's Packagist/subsplit path. These installer details are snapshot facts, not a guarantee that old globally installed versions support newer hooks. [Installer source](https://github.com/laravel/installer/blob/bf2273a52210819f768dd3e3f7f1e601befa9b5e/src/NewCommand.php).

For the documented package flow, the published repository needs a root `composer.json` with the package name and resolvable dependencies, plus a runnable Laravel skeleton: `artisan`, `bootstrap/app.php`, configuration/routes, public entrypoint, writable runtime directories, `.env.example`, and the initialization scripts expected by the installer. `type: project` is the appropriate Composer metadata, not a special Laravel kit API. A frontend kit also needs its package manifest/configuration and actual resources. The first-party React kit illustrates environment copying, key generation, SQLite initialization/migration, autoload/package discovery, frontend build/dev scripts, and optional installer hooks; its current Laravel 13/PHP 8.3 requirements must not be copied into a PHP 8.2 promise accidentally. [First-party kit composer.json](https://github.com/laravel/react-starter-kit/blob/main/composer.json), [Laravel skeleton](https://github.com/laravel/laravel/tree/12.x), [Composer package schema](https://getcomposer.org/doc/04-schema.md#type).

### How we'd do it

Keep the complete starter application in the monorepo and publish the agreed `gomighty/laravel-starter-kit` subsplit to Packagist. Give it released Composer/npm dependencies, the Mighty Astro directory/configuration, a small route rendering a real page, `.env.example`, and explicit install/build/dev scripts. Keep initialization idempotent because installer and Composer hooks can both participate. A clean `laravel new ... --using=gomighty/laravel-starter-kit` run is the acceptance test, including default database setup and working asset URLs. [Monorepo layout and release pipeline](https://github.com/gomighty/mighty/issues/42) and [create-mighty flow](https://github.com/gomighty/mighty/issues/45) must choose the starter's default framework/PHP version and how `npm create mighty` coordinates Composer and npm. Adapter support for Laravel 12 does not automatically require the starter's default to be Laravel 12.

## 4. Package tooling and provider setup

Testbench boots a Laravel application for package tests and lets a test case register package providers through `getPackageProviders()`. It supplies Laravel's testing facilities without checking in a full application for every unit/feature test. Its majors track Laravel: Testbench 10 is for Laravel 12, and 11 for Laravel 13. The inspected branch heads have narrower minima (`^12.55.0` and `^13.23.0` respectively), so testing the framework's earliest supported release requires choosing compatible historical Testbench versions rather than installing the newest head. [Testbench basics](https://packages.tools/testbench/the-basic), [10.x requirements](https://github.com/orchestral/testbench/blob/cd533cccfd8aab0002f2d37c58345be4da0cf178/composer.json), [11.x requirements](https://github.com/orchestral/testbench/blob/a326be05fc2375b6240b4ab5279a796e05b6d535/composer.json).

Pest 4 requires PHP 8.3 and builds on PHPUnit 12. Pest 3.8.3 supports PHP 8.2 and requires PHPUnit 11.5.33+. The optional Laravel plugin must match: plugin 3.2.0 supports Laravel 11/12; plugin **4.1.0** adds Laravel 13 and requires Pest `^4.4.1`, whereas plugin 4.0.0 does not allow Laravel 13. A Testbench-based Pest test case can avoid that plugin if its extra functions are not needed. [Pest 4 installation](https://v4.pestphp.com/docs/installation), [Pest 3.8.3 requirements](https://github.com/pestphp/pest/blob/v3.8.3/composer.json), [plugin 3.2.0](https://github.com/pestphp/pest-plugin-laravel/blob/v3.2.0/composer.json), [plugin 4.1.0](https://github.com/pestphp/pest-plugin-laravel/blob/v4.1.0/composer.json), [Pest test-case binding](https://v4.pestphp.com/docs/configuring-tests).

Larastan 3 is a PHPStan extension; the inspected requirements allow PHP `^8.2`, Laravel 12 and 13 components, and PHPStan `^2.2.2`. It boots an application container and falls back to Testbench for package analysis; the resolver reads Testbench configuration from the working directory. Include `vendor/larastan/larastan/extension.neon` (and Carbon's extension as documented), select source/test paths and a PHPStan level, then run `vendor/bin/phpstan analyse`. Monorepo working-directory/vendor-path choices therefore need one tested configuration. [Requirements](https://github.com/larastan/larastan/blob/ab26fdf90d84877061388109e1e251f67ca3ff7a/composer.json), [bootstrap](https://github.com/larastan/larastan/blob/ab26fdf90d84877061388109e1e251f67ca3ff7a/bootstrap.php), [package resolver](https://github.com/larastan/larastan/blob/ab26fdf90d84877061388109e1e251f67ca3ff7a/src/ApplicationResolver.php), [setup](https://github.com/larastan/larastan/blob/3.x/README.md).

Pint uses a root `pint.json`, with `{"preset":"laravel"}` a sufficient starting point; `vendor/bin/pint --test` checks without rewriting. Pint v1.32.1 requires PHP 8.3, while v1.24.0 supports PHP 8.2. A dev lockfile resolved on a newer PHP can therefore break the 8.2 job even though production dependencies support it. [Pint configuration](https://laravel.com/framework/docs/12.x/pint#configuring-pint), [v1.32.1 requirements](https://github.com/laravel/pint/blob/v1.32.1/composer.json), [v1.24.0 requirements](https://github.com/laravel/pint/blob/v1.24.0/composer.json).

The provider belongs in Composer `extra.laravel.providers` for auto-discovery. Register bindings and merge configuration in `register()`; register commands using `$this->commands([...])` while running in console, and register the precompiler after `blade.compiler` resolves. Composer `autoload.files` can load the global helper. [Package development](https://laravel.com/framework/docs/12.x/packages), [after-resolving example](https://github.com/inertiajs/inertia-laravel/blob/7963d48868a37f2e4cd36b60850e1c755a0d06ca/src/ServiceProvider.php), [helper autoload](https://github.com/inertiajs/inertia-laravel/blob/7963d48868a37f2e4cd36b60850e1c755a0d06ca/composer.json).

### How we'd do it

Use Testbench/Pest for the adapter's provider, helper/response, Blade execution, shared-context lifecycle, discovery/error handling, and HTTP client fake tests. Bind `Tests\TestCase` with `pest()->extend(...)->in(...)`. Keep one real application + real Node sidecar end-to-end job to cover process readiness, rendering, and asset serving, which HTTP fakes cannot prove.

Propose a Pest 3 lane for PHP 8.2/Laravel 12 and Pest 4 lanes for PHP 8.3+; retain common test syntax across them. Run Pint in one canonical PHP 8.3+ job or pin a PHP-8.2-compatible release if every matrix cell must install/run it. Resolve dependencies per matrix lane rather than reuse one incompatible lockfile. These are alternatives for [Monorepo layout and release pipeline](https://github.com/gomighty/mighty/issues/42) to settle, not changes to the map's PHP `^8.2` commitment. [Monorepo layout and release pipeline](https://github.com/gomighty/mighty/issues/42) and [Sidecar design](https://github.com/gomighty/mighty/issues/43) also own the Testbench/real-app split and exact end-to-end boot command.

## 5. Runtime versions, process wrapper, and HTTP calls

Laravel's published compatibility table supports Laravel 12 on PHP 8.2–8.5 and Laravel 13 on PHP 8.3–8.5. Composer floors are respectively `^8.2` and `^8.3`. Thus the map has **seven** valid runtime cells; PHP 8.2/Laravel 13 must be excluded. [Laravel support table](https://laravel.com/framework/docs/releases#support-policy), [Laravel 12 requirements](https://github.com/laravel/framework/blob/38486704d064d8c3dd1c546e9a2d7ffa13d2dfc4/composer.json), [Laravel 13 requirements](https://github.com/laravel/framework/blob/41807417bb85908412b67ff7ec4132a026d603c7/composer.json).

| PHP | Laravel 12 | Laravel 13 | Proposed test runner |
| --- | --- | --- | --- |
| 8.2 | Supported | Incompatible | Pest 3 / PHPUnit 11 |
| 8.3 | Supported | Supported | Pest 4 / PHPUnit 12 |
| 8.4 | Supported | Supported | Pest 4 / PHPUnit 12 |
| 8.5 | Supported | Supported | Pest 4 / PHPUnit 12 |

These are framework/runtime facts plus a proposed runner allocation, not a completed Composer solve for the future package. Current Testbench/plugin constraints also affect the lowest testable Laravel patch, as described above.

Symfony Process accepts argument arrays, a working directory and environment; `run()` blocks, `start()` runs asynchronously, callbacks stream stdout/stderr, and `stop()`/`signal()` control a running child. Its default timeout is 60 seconds; a long-lived sidecar wrapper needs `setTimeout(null)` or another explicit lifecycle policy. Laravel 12 requires Process `^7.2.0`; the inspected Laravel 13 permits `^7.4.5 || ^8.0.5`. A Mighty dependency restricted to compatible Process 7 releases can therefore cover both Laravel majors without forcing PHP 8.4 for Symfony 8. [Process documentation](https://symfony.com/doc/7.3/components/process.html), [Laravel 12 requirements](https://github.com/laravel/framework/blob/38486704d064d8c3dd1c546e9a2d7ffa13d2dfc4/composer.json), [Laravel 13 requirements](https://github.com/laravel/framework/blob/41807417bb85908412b67ff7ec4132a026d603c7/composer.json).

Laravel's HTTP client wraps Guzzle: `Http::post($url, $array)` sends JSON by default, `connectTimeout()`/`timeout()` bound calls, and connection failures throw `ConnectionException`. HTTP 4xx/5xx responses do not throw unless `throw()` is requested. `Http::fake()`, `preventStrayRequests()`, and request assertions support transport tests. [HTTP client](https://laravel.com/framework/docs/12.x/http-client).

### How we'd do it

Keep production PHP code syntactically valid on 8.2 and declare the Illuminate components actually used as `^12.0 || ^13.0`. Let Composer enforce the framework's higher floor when Laravel 13 is selected.

Make `artisan mighty:dev|build|start` thin wrappers around the installed `mighty-laravel` binary. Use an argument vector with an explicit project cwd, stream output, forward termination, reap the child, and return its exit code. Resolve the local installed executable without an implicit package download; command discovery across supported OS/package managers belongs in [Sidecar design](https://github.com/gomighty/mighty/issues/43). HTTP request handlers should connect to the already-running sidecar, not spawn a Node process for each render.

Use a dedicated HTTP transport class with explicit connection/render timeouts and deliberate non-success handling. Normalize props/shared context before JSON encoding; validate the returned status/body and any asset/error metadata. Avoid automatic retries until render idempotency is defined. Laravel auth guards, session stores, validation error bags, and CSRF state stay in PHP: functions like `user('guard')`, `session()` and `errors()` in Astro require an explicit serialized snapshot or a separately designed callback. A sidecar does not acquire PHP's live session/auth APIs merely by using the same URL.

The draft's claim about `Astro.request` also needs explicit forwarding: the current `MightyRenderRequest` contains component, props, context and partial only, and both container calls pass props/partial without the original backend request. [Sidecar design](https://github.com/gomighty/mighty/issues/43) and [Laravel adapter spec](https://github.com/gomighty/mighty/issues/44) must define URL/method/headers/body availability, forwarded values, and shared-context serialization before publishing that promise. [Current render request](https://github.com/gomighty/mighty/blob/6c7ca1d7ffab6494602db5d72720e764b8b00465/packages/core/src/types.ts), [dev container call](https://github.com/gomighty/mighty/blob/6c7ca1d7ffab6494602db5d72720e764b8b00465/packages/core/src/dev/render-vite.ts), [production call](https://github.com/gomighty/mighty/blob/6c7ca1d7ffab6494602db5d72720e764b8b00465/packages/core/src/start/index.ts).

## 6. Inertia's helper, factory, response, and sharing

Inertia Laravel 2.x offers a useful API reference. Its Composer-autoloaded `inertia()` helper returns the facade's `ResponseFactory` when called without a component, or delegates to `render()` otherwise. `Inertia::render()` uses the same factory via the facade accessor. `ResponseFactory::share()` stores values; `render()` normalizes `Arrayable` props, merges shared props with page props (page keys win), and constructs a `Response`. [Helper](https://github.com/inertiajs/inertia-laravel/blob/7963d48868a37f2e4cd36b60850e1c755a0d06ca/helpers.php), [facade](https://github.com/inertiajs/inertia-laravel/blob/7963d48868a37f2e4cd36b60850e1c755a0d06ca/src/Inertia.php), [factory](https://github.com/inertiajs/inertia-laravel/blob/7963d48868a37f2e4cd36b60850e1c755a0d06ca/src/ResponseFactory.php).

`Response` implements Laravel's `Responsable` contract. `toResponse($request)` resolves properties and constructs Inertia's page payload, then returns JSON for an Inertia request or the root Blade view for an initial request. The middleware contributes shared validation errors and applies version/root-view/sharing configuration before the controller response. This is a reference for the Laravel object boundary; Inertia's merged props and SPA protocol are separate design choices. Mighty's glossary instead keeps shared context outside props. [Response](https://github.com/inertiajs/inertia-laravel/blob/7963d48868a37f2e4cd36b60850e1c755a0d06ca/src/Response.php), [middleware](https://github.com/inertiajs/inertia-laravel/blob/7963d48868a37f2e4cd36b60850e1c755a0d06ca/src/Middleware.php), [Mighty vocabulary](https://github.com/gomighty/mighty/blob/6c7ca1d7ffab6494602db5d72720e764b8b00465/CONTEXT.md).

Inertia's optional SSR HTTP gateway posts a page payload, expects separate head/body results, and returns `null` for most dispatch failures so client rendering can continue. Mighty requires server rendering, so silently copying that fallback would hide a failed render. [Inertia SSR gateway](https://github.com/inertiajs/inertia-laravel/blob/7963d48868a37f2e4cd36b60850e1c755a0d06ca/src/Ssr/HttpGateway.php).

### How we'd do it

Expose `mighty()` as the factory and `mighty('posts.index', $props)` as a `MightyResponse` implementing `Responsable`; a facade may delegate to the same factory. Defer request-dependent context resolution to response/view execution, normalize JSON data there, then delegate one render request to the transport. Preserve shared context separately from props.

Keep globally registered context-provider callbacks separate from their per-request resolved values. Use request-scoped state or an explicit reset lifecycle for mutable context and assets so Octane/other long-lived workers cannot leak one request's values into another. [Laravel adapter spec](https://github.com/gomighty/mighty/issues/44) should specify `share()`'s accepted forms, callback timing, precedence, return types/status/headers, and how Blade partial rendering relates to full controller responses. The draft's callback-only `share(fn () => [...])` is a proposed Mighty API; it is not Inertia's `share()` signature.

## Decisions handed forward

- **[Laravel adapter spec](https://github.com/gomighty/mighty/issues/44):** precise Blade grammar, supported attribute forms/slots, full versus partial response API, shared-context lifecycle/serialization and documented utilities, request forwarding, and asset placement with Livewire.
- **[Sidecar design](https://github.com/gomighty/mighty/issues/43):** discovery file/readiness/ownership, browser asset versus local render URL, transport errors/timeouts, structured assets, child-process lifecycle, and development error presentation.
- **[Monorepo layout and release pipeline](https://github.com/gomighty/mighty/issues/42):** PHP 8.2 test tooling versus Pest 4, canonical Pint job/version, dependency resolution/minimum-version policy, and starter publication/version choice. The Testbench/real-app strategy remains dependent on this and the sidecar decision.
- **[create-mighty flow](https://github.com/gomighty/mighty/issues/45):** reliable Laravel starter creation and coordination of Composer/npm setup.

No research finding requires reversing the map's PHP/Laravel support decision. Runtime compatibility and development tooling compatibility must be specified separately.
