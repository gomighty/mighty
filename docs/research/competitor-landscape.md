# Competitor landscape: Astro rendering from another backend

Research for [Competitor landscape: does anything already render Astro from a foreign backend?](https://github.com/gomighty/mighty/issues/30), part of [Map: the way to Mighty 0.1.0](https://github.com/gomighty/mighty/issues/29). Checked 2026-09-11 against first-party documentation, source, GitHub releases/commits, npm metadata, and Packagist metadata. This report records evidence; it does not decide whether Mighty continues.

**Verdict against the agreed criterion:** No unambiguous match was established for an independently hosted backend rendering Astro pages with dev HMR; Astro 7's maintained native Hono integration is a strong, interpretation-dependent match that prevents an unconditional “nothing already does this” conclusion.

The criterion is a maintained library that renders `.astro` pages on demand from a non-Astro backend with dev HMR. It does not require several backend languages, Inertia compatibility, a particular rendering API, or a sidecar. The distinction between an independent backend and Hono used as Astro's request entrypoint needs to remain visible: it is an interpretation of “non-Astro backend,” not an extra settled requirement. Mighty's [domain vocabulary in the map Notes](https://github.com/gomighty/mighty/issues/29) describes adapters handing render requests to Mighty; reverse-proxy integration and Astro-owned page routing are useful alternatives with different boundaries.

“Maintained” below means positive recent release/development evidence or an explicit maintainer commitment. It is not a support guarantee. “No HMR evidence” means the inspected docs and implementation do not establish it, rather than a claim that adding it is impossible. Dates are UTC calendar dates. npm dates are publication dates; GitHub release publication dates and commit dates are identified separately. A `0.x` version can be the normal distribution channel even when its authors call the project alpha.

## What the close candidates establish

Astro 7 materially changes the Hono comparison. The official example uses a real Hono app and lets that app decide which Astro handlers run and in what order. Astro's `pages()` handler still selects from Astro's route manifest. The documented entrypoint is inside the Astro project. This is evidence for a Hono-driven request pipeline with Astro rendering, and against saying developers must always use Astro's fixed middleware pipeline. It does not prove a reusable bridge for an existing independent backend process. [Routing guide](https://docs.astro.build/en/guides/routing/#advanced-routing), [FetchState and pages](https://docs.astro.build/en/reference/modules/astro-fetch/)

Two readings of the current criterion therefore produce different outcomes:

- If a Hono app exported as Astro's request entrypoint qualifies as a non-Astro backend, native Astro 7 is a plausible match. The remaining verification is an end-to-end check that `.astro` page and island edits update through that Hono entrypoint, rather than assuming the behavior from the general development documentation. [Hono guide](https://docs.astro.build/en/guides/routing/#using-with-hono), [development behavior](https://docs.astro.build/en/develop-and-build/#work-in-development-mode)
- If the criterion means an independently hosted backend using Astro as its rendering layer, the best direct library found is `@casoon/fragment-renderer`, with no established dev HMR. Storybook Astro demonstrates maintained Container rendering and HMR, but its documented workflow is story previews. Neither result justifies claiming that a production backend bridge with dev HMR is technically unavailable. [Node adapter](https://github.com/casoon/fragment-renderer/blob/main/src/adapters/node.ts), [Storybook framework](https://github.com/storybook-astro/storybook-astro)

This report does not silently require a named-component API, PHP support, or a sidecar to disqualify a candidate. Those could be product differentiators, but they are not in the agreed kill criterion.

## Search coverage and limits

The survey inspected all projects named in the ticket, then followed relevant first-party discoveries. Queries included `astro inertia`, `astro laravel`, `astro backend`, `astro container`, and combinations with `render`, `HMR`, `Express`, and `Hono`. GitHub repository searches covered name/description and a TypeScript README query; npm searches inspected up to 250 ranked results per term pair. Packagist searches used the exact term pairs and `astrojs`. This is a bounded discovery survey, not an exhaustive census or a runtime compatibility audit.

No independent maintained Inertia-for-Astro client/page adapter was identified. GitHub's name/description query surfaced the Mighty-named Laravel playground; exact npm package lookups for `astro-inertia` and `inertia-astro` returned 404. Broad npm searches surfaced normal Inertia adapters and `astro-laravel`, whose runtime is Blade. This is a negative search result, not proof that no obscure or unpublished implementation exists. [GitHub query API](https://api.github.com/search/repositories?q=astro%20inertia%20in%3Aname%2Cdescription), [npm query API](https://registry.npmjs.org/-/v1/search?text=astro%20inertia&size=250), [astro-laravel documentation](https://github.com/sijad/astro-stencil/tree/main/packages/astro-laravel)

Packagist's `astro inertia` hit, `tonka/astro`, describes an Inertia/React starter, not Astro.build. `astro backend` found Flastro. Many bare `astro` hits concern astronomy or unrelated vendor names. These name collisions were excluded. [Inertia query](https://packagist.org/search.json?q=astro%20inertia&per_page=100), [backend query](https://packagist.org/search.json?q=astro%20backend&per_page=100), [Laravel query](https://packagist.org/search.json?q=astro%20laravel&per_page=100)

Release metadata was checked directly because indexed package pages sometimes lagged the live repository or registry. No-release statements refer specifically to the checked release channel; for example Storybook Astro publishes on npm despite having no GitHub Releases entries. Source assertions without runtime testing remain marked as such.

## Evidence for the later comparisons pass

The existing [comparisons page](../../packages/docs/src/content/docs/guides/hello-world/comparisons.mdx) should explain HonoX's JSX SSR/islands and distinguish Inertia protocol adapters from Astro rendering. The new `@hono/inertia` package is worth including alongside Antenna. [HonoX](https://github.com/honojs/honox), [Hono Inertia](https://github.com/honojs/middleware/tree/main/packages/inertia)

The Astro comparison should account for the native Hono entrypoint introduced in Astro 7; the old blanket claim that developers are bound to Astro's middleware design is too broad. `astro-laravel` deserves its own comparison as Astro-authored Blade, and Mingle should be described as browser-mounted React/Vue components in Livewire. [Advanced routing](https://docs.astro.build/en/guides/routing/#advanced-routing), [astro-laravel](https://github.com/sijad/astro-stencil/tree/main/packages/astro-laravel), [Mingle](https://github.com/ijpatricio/mingle)

For Fusion, the checked first-party evidence supports early-preview status, Vue/Inertia architecture, and stale release activity. It does not substantiate the existing explanation that confusion, lack of React support, or lack of community interest caused suspension. Remove or separately source those motives. This report also does not validate any current Mighty support claims or roadmap promises appearing in the comparison page. [Fusion README](https://github.com/fusion-php/fusion), [release history](https://github.com/fusion-php/fusion/releases)
