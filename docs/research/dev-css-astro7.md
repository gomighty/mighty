# Dev CSS without vendored Astro code

Research for [Dev CSS without vendored Astro code](https://github.com/gomighty/mighty/issues/32), checked 2026-09-11 against Mighty `6c7ca1d7ffab6494602db5d72720e764b8b00465` and Astro **7.3.2** / Vite **8.0.13** tagged source. This is a planning recommendation for [Dev CSS approach decision](https://github.com/gomighty/mighty/issues/40), not an implementation or a compatibility certification.

## Recommendation

There is **no public CSS-collection replacement** for the current Container rendering path in Astro 7.3.2. Keep ownership of a small, version-bounded CSS adapter for the 0.1 upgrade. First probe Astro's existing per-route CSS virtual module as the smallest concrete alternative to copied traversal. Adopt it only if it passes the acceptance checks below; otherwise retain vendoring and port the necessary Astro 7 behavior. Do not assume the current copied algorithm is correct merely because Vite still exposes its old methods. This recommendation leaves the final approach and pin policy to the Dev CSS approach decision.

The strongest long-term public-facing alternative is rendering actual injected Astro routes through the dev server, but that changes the rendering contract and deserves its own design/prototype. Removing roughly 250 lines of copied traversal does not justify silently changing Mighty props, context, partial rendering, or backend routing.

## What changed in Astro 7

Mighty's copy imports the target with `viteServer.ssrLoadModule`, walks the merged graph and reads `ModuleNode.ssrModule`, loading CSS again with `?inline` when needed. Its resolver separately translates renderer imports into URLs under the caller's dev address. These are separate responsibilities: removing copied CSS traversal does not remove `createResolve()` while Container still renders hydration scripts. [Current CSS](../../packages/core/src/dev/css.ts), [resolver](../../packages/core/src/dev/resolve.ts), [render assembly](../../packages/core/src/dev/index.ts)

Astro 7's replacement uses environment-local graphs and `fetchModule`, not `ssrModule` as a readiness signal. It recursively fetches untransformed child modules, including dynamically imported components; stops at propagated-content assets; traverses depth-first; and reads CSS from a shared transform cache. Its own comments explain that reprocessing CSS modules with `?inline` can change Lightning CSS scoped-name hashes. Missing cached content falls back to an empty string in generated CSS records, so blindly converting all results to inline style tags is unsafe. Its module-loading walk also skips CSS collector virtual modules to avoid circular pending-request deadlocks. These are concrete responsibilities to preserve, not an invitation to replace the old walk with a two-line DFS. [Tagged CSS implementation](https://github.com/withastro/astro/blob/astro%407.3.2/packages/astro/src/vite-plugin-css/index.ts)

Vite 8.0.13 retains `ssrLoadModule` and the mixed compatibility graph. Its separate `SSRCompatModuleRunner` disables runner HMR and populates `ssrModule`; replacing only the loader with `environment.runner.import` removes that population assumption. This does not prove browser HMR is broken today: browser updates and server runner invalidation are separate paths. It does mean loading, graph traversal and invalidation must be tested as a unit. [Compatibility loader](https://github.com/vitejs/vite/blob/v8.0.13/packages/vite/src/node/ssr/ssrModuleLoader.ts), [mixed graph](https://github.com/vitejs/vite/blob/v8.0.13/packages/vite/src/node/server/mixedModuleGraph.ts)

## Concrete virtual-module probe

Use the existing Astro-configured server, obtain the **SSR runnable environment**, and import `virtual:astro:dev-css:<route.component with the extension dot encoded as @_@>` through that environment's runner. Obtain `route.component` from Astro's route metadata; do not substitute an absolute filesystem path for its project-relative component name. The page plugin matches the decoded name against its routes list. Keep the ID convention in one internal adapter, with an explicit Astro version contract. The plugin's tagged ID helper is the source of the encoding, not a public import. [ID helper](https://github.com/withastro/astro/blob/astro%407.3.2/packages/astro/src/vite-plugin-css/util.ts), [page IDs](https://github.com/withastro/astro/blob/astro%407.3.2/packages/astro/src/vite-plugin-pages/util.ts), [page lookup](https://github.com/withastro/astro/blob/astro%407.3.2/packages/astro/src/vite-plugin-pages/page.ts)

Render and collect through compatible environment paths; assert the returned Set shape and reject unresolved/missing page metadata instead of accepting empty CSS as success. Check cold startup before a browser has fetched any client modules. Astro's collector populates the current environment graph using `fetchModule`, while its content cache is shared across plugin environments. Whether SSR-only initialization supplies correct content for every fixture, and whether importing a cached virtual module sees newly added/removed child styles, are runtime questions. Do not treat an initial successful CSS response as proof of invalidation correctness. The exact loading call is a prototype proposal inferred from source; it has not been executed in this research. [CSS plugin](https://github.com/withastro/astro/blob/astro%407.3.2/packages/astro/src/vite-plugin-css/index.ts)

For nonempty content, preserve style IDs used by Vite's browser updater. Determine how to handle empty content using Astro's own runtime asset behavior rather than silently emitting an empty style; test the URL fallback, caller dev address and base prefix if external links are needed. The probe must cover style edits, new imports, removed imports and repeated requests before deciding whether direct virtual-module consumption is sufficient or requires private invalidation hooks. Keep `resolve.ts` unless a separate route-rendering change makes it unnecessary.

## Synthetic-route implications

The public integration route mechanism supplies a path and entrypoint. A wrapper can look up an allowlisted target and render it with supplied props. An in-process opaque request token could reference payload/context without serializing arbitrary values; an actual HTTP proxy instead requires a serialization contract and loses implicit process-local context. These are proposed designs, not APIs Astro already provides. Concurrent requests require isolated payload lifetime and cleanup. Routing must preserve original URL semantics, errors and the backend's routing ownership. [Integration route API](https://docs.astro.build/en/reference/integrations-reference/#injectroute-option), [Mighty render contract](../../packages/core/src/dev/render-vite.ts)

A single dispatcher that statically imports every page risks collecting every page's CSS because Astro traverses imported and dynamically imported graph dependencies. Prefer per-component wrappers or demonstrate that a dispatcher preserves CSS isolation. A route rendered as an endpoint returning Container HTML would still bypass page asset injection and would not solve the original problem. Partial rendering also needs explicit preservation: the Container defaults and per-request `partial` setting cannot simply be presumed equivalent to Astro's route output. These are source-derived risks to validate against the page collector and Mighty's current tests. [Collector](https://github.com/withastro/astro/blob/astro%407.3.2/packages/astro/src/vite-plugin-css/index.ts), [basic tests](../../packages/core/tests/dev/basic.test.ts)

Normal route rendering should reduce duplicated integration handling because Astro runs its real configuration and page pipeline. However React renderer/client assets, Alpine page scripts and Partytown head-inline scripts must then be emitted once, so remove Mighty's duplicate injection only after equivalence is demonstrated. Preserve asset URLs, Vite client requests and websocket access through the backend/base path. A real listening dev server may simplify current lifecycle shims, but internal middleware mode still needs the startup and cleanup investigation already recorded in Astro 7 upgrade impact on the internals core relies on. [Current assembly](../../packages/core/src/dev/index.ts), [prior research](https://github.com/gomighty/mighty/blob/e77d9bedbda4c7592093636ef50465bc3386a6a5/docs/research/astro-7-upgrade-impact.md)

## Proposed pin and drift policy for the Dev CSS approach decision

Pin **exact Astro and direct Vite versions** for the first proven upgrade pair (7.3.2 / 8.0.13 is the investigated candidate, not yet a tested pair). An exact minor range such as `~7.3.2` still accepts patch changes; a caret accepts minor changes too. Since both Container and the proposed CSS virtual-module contract lack stable guarantees, neither is justified by this audit. Align official integrations with the selected Astro major and commit the lockfile. Check installed resolution so core and Astro do not silently load incompatible Vite majors. The package declares Vite `^8.0.13`; exact pinning here is a project recommendation, not an upstream requirement. [Astro package](https://github.com/withastro/astro/blob/astro%407.3.2/packages/astro/package.json), [Container stability warning](https://docs.astro.build/en/reference/container-reference/)

Record upstream tag/commit, source path, license attribution and deliberate local deviations alongside each adapter. Keep the historical citation for the old vendored algorithm; add the new provenance when porting it. A raw equality test against the old deleted upstream file cannot detect current semantic drift. Prefer a scheduled or dependency-update check that compares the chosen upstream CSS plugin, page-ID helpers, loader and resolver sources against a stored reviewed baseline and opens an update for review. Gate each accepted dependency update on behavior tests. If exact source-copy comparison is used, compare a pristine upstream snapshot separately from Mighty's modified file. Do not silently update pins when a source hash changes.

## Acceptance and evidence limits

Before adopting either the virtual module or updated vendoring, verify:

- Cold-start inline page CSS, nested child CSS, dynamic child imports, CSS modules (including Lightning CSS), imported global CSS/preprocessors, order and deduplication, and content-entry propagation isolation.
- Browser CSS edits plus adding/removing an import, repeat render requests, and request concurrency. Confirm styles update without stale/duplicate tags and that deleted styles disappear; exercise partial navigation according to the chosen CSS policy.
- React server markup **and actual hydration**, Alpine behavior and Partytown script/library requests, with no duplicated injected scripts. Check URL resolution under the existing dev base and a caller-provided address, including Vite websocket traffic.
- Startup/shutdown outside Vitest, existing context/props/full-page/partial/error behavior, then `pnpm build`, `pnpm run typecheck`, `pnpm run ci:biome`, and `pnpm test` in that order.

Existing tests cover page/child CSS, React markup and renderer URL fetching, Alpine module fetching and Partytown injected text. They do not demonstrate live browser hydration or CSS HMR. [Basic tests](../../packages/core/tests/dev/basic.test.ts), [React tests](../../packages/core/tests/dev/react.test.ts), [Alpine tests](../../packages/core/tests/dev/alpinejs.test.ts), [Partytown tests](../../packages/core/tests/dev/partytown.test.ts)

This research read exact tagged upstream source and current local code. No Astro 7 runtime probe, synthetic route prototype or implementation was performed. The coordinating agent verified the current lockfile: build and typecheck passed; 12 test files / 50 tests passed. Plain `ci:biome` encountered a preexisting nested root configuration in `.context/research-worktree/biome.json`; the same Biome check restricted to the 107 Git-tracked files passed. These are baseline results, not evidence that any candidate works on Astro 7.
